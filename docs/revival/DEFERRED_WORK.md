### 1. MongoDB 트랜잭션 운영 환경 검증

현재 결제 승인, 결제 취소, 재고·쿠폰·포인트 확정 및 판매자 승인·반려 감사 기록에 MongoDB 트랜잭션을 사용한다. 트랜잭션은 MongoDB replica set 또는 Atlas 환경이 필요하다.

- [ ] 실제 운영 MongoDB가 replica set으로 구성되어 있는지 확인
- [ ] 스테이징 DB에서 결제 승인 중간 실패 시 전체 롤백 검증
- [ ] 판매자 승인 중 SellerInfo 저장, User 역할 변경 또는 감사 로그 저장 실패 시 롤백 검증
- [ ] 판매자 반려 중 SellerInfo 저장 또는 감사 로그 저장 실패 시 롤백 검증
- [ ] 트랜잭션 재시도 및 타임아웃 정책 확인

완료 조건: 의도적으로 중간 오류를 발생시켜도 주문, 재고, 쿠폰, 포인트, 사용자 역할이 부분 저장되지 않아야 한다.

### 2. 기존 DB 데이터 마이그레이션

SellerInfo에 `draft`, `submittedAt`, `approvedAt` 상태가 추가됐고 사업자번호는 10자리 숫자로 정규화되기 시작했다. 기존 데이터는 여전히 하이픈 포함 번호나 예전 상태를 가질 수 있다.

- [x] 기존 사업자번호를 숫자 10자리로 정규화하는 마이그레이션 도구 작성
- [x] 정규화 후 활성 판매자의 중복 사업자번호 충돌 목록을 사전에 출력
- [x] 기존 신청 데이터의 `status`, `submittedAt`, `approvedAt`, `rejectedAt` 보정 규칙 구현
- [x] 사업자번호 unique index는 soft-delete되지 않은 판매자에게만 적용하도록 정책 확정
- [ ] 스테이징 DB에서 dry-run 보고서를 검토하고 잘못된 번호·충돌 데이터 정리
- [ ] 백업 확인 후 스테이징 및 운영 DB에 마이그레이션 적용
- [ ] 실제 DB에서 CheckoutSession TTL 및 StockReservation 만료 조회 인덱스 확인

실행 도구: 서버 저장소에서 `npm run migrate:seller-applications`를 실행하면 기본적으로 읽기 전용 dry-run 보고서만 출력한다. 실제 변경은 백업을 확인한 후에만 `npm run migrate:seller-applications -- --apply --backup-confirmed`로 실행한다. 유효하지 않은 번호나 활성 판매자 번호 충돌이 하나라도 있으면 적용은 자동 중단된다.

인덱스 정책: `CheckoutSession`은 만료 세션 자동 제거를 위해 TTL을 사용한다. `StockReservation`은 TTL을 사용하지 않는다. 활성 예약은 애플리케이션 로직이 재고를 복구하고 `released` 이력을 남겨야 하므로 `{ status, expiresAt }` 조회 인덱스만 유지한다.

- [ ] 동일 승인·취소 요청 반복 시 멱등성 확인

현재 제한: 부분 환불은 지원하지 않고 전액 환불만 허용한다.
